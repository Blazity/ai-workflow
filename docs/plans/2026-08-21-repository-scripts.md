# Pre-PR checks v2: niezawodne, konfigurowalne, bez wbudowanego auto-fixu

Po zatwierdzeniu skopiować jako `docs/plans/2026-08-20-pre-pr-checks-v2.md` (konwencja repo). Wykonanie: `/opus-orchestration` na tabeli etapów poniżej.

## Kontekst / Problem

Pre-PR checks failują niezależnie od zdrowia kodu, a użytkownik nie widzi dlaczego:
- **Sufit ~300 s na inwokację Vercela**: cały batch (setup + checki + cykle fix) siedzi w jednym `"use step"` `runPrePrChecksStep` i ginie jako "terminated"/"exceeded max retries" (potwierdzone na naszym prodzie: `wrun_01M0CGC9GEMEBC3THA2DNBECNJ`, 358631 ms, i u Arthura). Wzorzec naprawy istnieje w repo (trio detached faz), ale nie jest podpięty do checków.
- **Sandbox = gołe node24** (manager.ts:99): `uv`/python = exit 127; prywatny rejestr npm Arthura = 404, bo do sandboxa nie dociera ŻADNA zmienna środowiskowa (Sandbox.create i runCommand bez `env`).
- **Wbudowana pętla auto-fix** (do 3 cykli agenta, ~811 s) maskowała porażki (zielone runy "dzięki" naprawie) i paliła budżet na nienaprawialne (brak binarki, 404). PR #320 (default 0) to odsłonił. Weryfikacja auto-fixa na prodzie (inna sesja): cap i notyfikacja działają, ale finalize pada na stale head (AIW-310, osobny defekt).
- **Raportowanie**: finalize mówi mylące "The checks could not be started" (w tym przy missing_gate, gdy checki PRZESZŁY - UP-4847), a produkt nigdzie nie nazywa padniętej komendy (AIW-309), mimo że `formatPrePrCheckFailures` buduje pełne summary.
- **Budżet**: JOB_TIMEOUT_MS (default 30 min) to jednocześnie lifetime sandboxa i budżet czasu runu - długie suity testów fizycznie nie mieszczą się obok pracy agenta.

Decyzje produktowe (Jakub, DM 19.08 + wymagania z review 17.08): auto-fixu przy padniętym checku ma NIE być ("Nie, nie powinno"); fix agent podpinany OPCJONALNIE według outcome; komendy typu `yarn test` mają po prostu działać; pole "Fix cycles" znika z UI; użytkownik definiuje środowisko workspace (toolchainy); reaktywny workflow na checki GitHub Actions oraz dobór wersji node z package.json = OSOBNE plany; "zróbmy plan najpierw".

Ustalenia ze spotkania 21.08 (transkrypcja meeting-threads-2026-08-21.md, wątek 9 + zasady przekrojowe): per-repo config z nazwanymi grupami komend potwierdzony jako kierunek; tooling-agnostic (zero założeń o npm/Node); setup wykonywany PRZY TWORZENIU workspace, nie w batchu; uczciwe kontrakty bloków (Prepare Workspace nie może robić rzeczy spoza nazwy); "don't over-engineer"; lifecycle hooks vs custom nazwy ZAPARKOWANE - nasz plan to godzi (nazwy wolne, bramka wskazuje wymagane grupy przez binding, nie przez zarezerwowaną nazwę). Obserwowalność to największa skarga ("one big black box"): wyniki per komenda + copy-to-clipboard adresują ją w tym planie.

Uzupełnienie Jakuba (20.08, po review planu): (1) nazwa bardziej generyczna: "scripts"/"cli"/"shell" albo kombinacja, nie "pre-PR checks"; (2) custom NAZWANE grupy skryptów per repo (np. test, lint, prettier fix), odpalane potem z bloku (np. CLI): jedna lub wszystkie; (3) OTYPOWANE wyniki: możliwość sprawdzenia w branchu, czy wszystkie się powiodły albo czy jeden się powiódł, z autocomplete (analogia do wymagania typowanego "flagged" z injection check).

**Stan maina 21.08 (e84fd311), zweryfikowany w kodzie - koryguje starszy recon:** sufit 300 s jest JUŻ rozwiązany: `runPrePrChecksWithFixes` (workflows/blocks/pre-pr-checks.ts:168-176) świadomie nie jest krokiem; jeden detached batch per repo per fixCycle (`startRepoCheckBatchStep` runner.ts:283, maxRetries=0) + `pollPhaseUntilDone` poza krokiem (pre-pr-checks.ts:368). Wyniki per komenda + bounding + `phase: setup|workspace|batch|omitted` istnieją (runner.ts:63-136). `MAX_PRE_PR_FIX_CYCLES = 0` (runner.ts:31, registry :779) - repair wyłączony domyślnie, ale cała maszyneria (startPrePrRepairStep/collectPrePrRepairStep/runFixCycle, pre-pr-checks.ts:642-692) nadal w kodzie. Kontrakt outputu z `gate` + recovery (finalize-workspace.ts:42) stoi. NADAL BRAK: grup/env w configu, jakiegokolwiek `env` w runCommand, timeoutu per komenda (batch stall -> phase "batch"), przywracania czystości drzewa (workspace-gate.ts:194-203 dalej pada na modyfikacji), osobnego budżetu checków (batchCapMs = min(PRE_PR_CHECK_BATCH_MAX_MINUTES, remaining+60 s) - poll konsumuje budżet runu), bloku run_scripts, komentarza Jira z padniętą komendą, setupu przy workspace (dalej w batch skrypcie).

Decyzje Filipa (grilling, ta sesja): usunąć pętlę całkowicie; setup phase + presety zamiast zmiany runtime'u; `env` jako NAZWY zmiennych per repo; pełna widoczność porażek; jeden detached batch; jeden silnik dla obu bloków; bez nowego bloku fix agenta (weryfikacja + docs); UI: edytor env + usunięcie Fix cycles; **checki mają własny limit czasu, NIE wliczany w budżet runu** (nie jedna zmienna na wszystko); zero pasujących checków = głośne `skipped`, PR przechodzi.

## Solution (perspektywa użytkownika)

Domena przemianowana z "pre-PR checks" na generyczne **Repository scripts**: per repo definiuje się fazę `setup` oraz NAZWANE grupy skryptów (test, lint, prettier-fix...), plus `env` (nazwy zmiennych z allowlisty). Generyczny blok `run_scripts` odpala jedną, kilka lub wszystkie grupy; bramka publikacji (dotychczasowy blok pre-PR) to cienki adapter wskazujący grupy wymagane przed PR-em. Wykonanie działa w ramach własnego limitu czasu (niezależnego od budżetu runu), zwraca wynik per komenda (repo, komenda, exit code, czas, ogon outputu) i OTYPOWANY outcome (enumy per grupa + `allPassed`/`anyFailed`), branchowalny z autocomplete - bez pętli naprawczej. W Jira i w szczegółach runu widać dokładnie co padło; "nie przeszły", "nie mogły wystartować" i "nic nie pasowało" to trzy rozróżnialne stany. Przerwany batch raportuje częściowe wyniki.

## User stories

1. Jako operator chcę, żeby batch checków >5 min kończył się wynikiem, nie "terminated" - długie suity są możliwe w ramach limitu fazy checks, niezależnego od budżetu runu.
2. Jako admin klienta chcę per repo fazę setup (instalacja uv, PATH) i listę komend, żeby checki działały na repo pythonowym i yarnowym w jednym sandboxie node24.
3. Jako admin chcę wskazać per repo nazwy zmiennych (np. GITLAB_UNIFY_FRONTEND_TOKEN) z allowlisty operatora, żeby komendy widziały sekrety bez wklejania ich w komendy i bez zapisu w DB; wartości nigdy nie wyciekają do outputów/Jiry.
4. Jako użytkownik chcę po padniętym checku zobaczyć w Jira/dashboardzie repo, komendę, exit code i ogon outputu; po przerwanym batchu - wyniki częściowe ("przerwano po 12 z 17").
5. Jako autor workflow chcę branchować na outcome bloku (passed/failed/skipped/missing_configuration) i opcjonalnie podpiąć agenta naprawczego - domyślnie NIC nie jest podpięte.
6. Jako operator chcę odróżnić "kod nie przeszedł checków" od "checki nie mogły wystartować" (setup/env/infra) od "żaden check nie pasował" (skipped, głośne, PR przechodzi).
7. Jako użytkownik chcę, żeby wisząca komenda (watch mode, prompt interaktywny) skończyła się wynikiem "timed out after N s" z nazwą winowajcy, a nie zjadła całego runu.
8. Jako autor workflow chcę zdefiniować per repo nazwane grupy skryptów (test, lint, prettier-fix) i odpalić z bloku jedną, kilka lub wszystkie - także poza kontekstem PR-a.
9. Jako autor workflow chcę branchować na otypowanych wynikach (enum per grupa, `allPassed`/`anyFailed`) z autocomplete w edytorze, zamiast porównywać wolny tekst.

## Implementation decisions

- **Nazewnictwo i kształt konfiguracji**: domena to "Repository scripts" (ekran /scripts zamiast /checks). Per repo: `setup: string[]` + `groups: { [nazwa]: { commands: string[], extends?: string[] } }` + `env?: string[]` + opcjonalne limity. Grupa może rozszerzać inne grupy (composite, np. `verify` = extends: [test, lint, build]); walidacja: referencje istnieją, zero cykli (DAG), ekspansja topologiczna z deduplikacją zachowującą kolejność. Stary kształt (`commands: string[]`) normalizowany PRZY ODCZYCIE do `groups: { checks: { commands } }` (tabela wersji append-only zostaje, zero migracji DB); zapis zawsze w nowym kształcie. Bramka publikacji wskazuje grupy wymagane przed PR-em (default: wszystkie).
- **Setup przy tworzeniu workspace, jako WIDOCZNY podkrok** (uczciwe kontrakty: Prepare Workspace klonuje, osobny podkrok "Setup environment" instaluje toolchainy per repo i raportuje wyniki w run details). Dzięki temu agent ma toolchain także w fazie implementacji (może sam odpalać testy). Silnik skryptów przed batchem tylko weryfikuje marker setupu per repo i doinstalowuje, gdy brak (odporność na resume/nowy sandbox). Padnięty setup = głośny błąd klasy "could not be started" wcześnie w runie, nie w połowie.
- **Generyczny blok `run_scripts`**: nowy typ bloku w rejestrze; parametry: wybór grup (jedna, wiele, wszystkie) i opcjonalnie zakres repo; używa tego samego silnika. `run_pre_pr_checks` NIE jest przemianowywany w miejscu: zostaje jako cienki adapter bramki publikacji (deployowane definicje działają dalej; para `outcome`+`gate` dla recovery zostaje tam).
- **Otypowane wyniki**: output obu bloków z enumami per grupa (`passed | failed | timed_out | skipped | not_run`) + zagregowane `allPassed: boolean` i `anyFailed: boolean`; bindingSchema niesie enumy, żeby branch w edytorze podpowiadał wartości (autocomplete) zamiast porównywać wolny tekst.
- **Silnik = jeden głęboki moduł** (`apps/worker/src/pre-pr-checks/`), interfejs w trzech fazach na granicach kroków WDK: `startCheckBatch(config, workspace, resolvedEnv) -> handle {commandId, sentinelFile, resultsDir}` (krok, maxRetries=0), istniejący `pollPhaseUntilDone` (orkiestracja poza krokiem), `collectCheckBatch(handle) -> wyniki per komenda` (krok, wołany TAKŻE po przerwaniu - partial results). Silnik przyjmuje WYBÓR GRUP do wykonania. Wszystkie trzy bloki (`run_scripts`, bramkowy `run_pre_pr_checks`, report-only `run_checks` v1) to adaptery.
- **Skrypt-runner** (generowany, pisany do sandboxa, nigdy do DB): repo po repo, weryfikacja markera setupu (re-run setupu tylko gdy marker nieobecny), każda komenda przez własny `bash -lc` (login shell - PATH z profilu widoczny dalej); wynik per komenda do pliku w katalogu kluczowanym `commandId` + lockfile (odmowa startu przy zajętym kluczu); sentinel na końcu; per-command timeout (default z env, override w configu) zapisywany jako zwykły wynik "timed out"; heurystyka "exit 0, ale deps nienainstalowane" liczona w sandboxie na PEŁNYM outputcie (do collect idzie head+tail); padnięty setup przerywa repo i znaczy `setupFailed`; po batchu skrypt przywraca czystość śledzonych plików (`git checkout -- .` per repo) i raportuje, które komendy zabrudziły drzewo - inaczej bramka czystości publikacji ubija run ("Run Workspace is not clean").
- **Pętla auto-fix znika**: `runFixAgent`, `MAX_PRE_PR_FIX_CYCLES`, repair sentinel - usunięte. UWAGA kontrakt: klucz `maxFixCycles` ZOSTAJE w schematach (`schema.ts:219-227,764-766` są `.strict()`) jako przyjmowany-i-ignorowany; `block-registry.ts:774` przestaje go wpisywać w defaults nowych definicji; pole `fixCycles` w output = stałe 0 (bindingSchema wymaga). Ręczny mirror: `docs/workflow-workspace/index.html:1056-1064` + `BLOCK_PARAM_KEYS`.
- **Wyjście porażki = `kind:"next"` + branch na `outcome`** (NIE failure port: interpreter odrzuca `kind:"next"` z FAILURE_PORT jako unknown port, a ścieżka `execution_error` nie zapisuje `steps[id]`, więc nie niesie outputu do fix agenta). Docs example okablowania fix agenta używa brancha na outcome.
- **Kontrakt outputu bloku** rośnie o wyniki per komenda (`failures[]`/`results[]`), zachowując parę `outcome` + `gate` - `recoverPrePrGateFromSteps` (`finalize-workspace.ts:42-62`) rozpoznaje po niej output przy odzyskiwaniu bramki; zmiana `statusVariants` dzieje się razem ze zmianą kontraktu (walidator: `executionError(category:"schema")`).
- **Budżet fazy checks**: własny limit (env `PRE_PR_CHECK_BATCH_MAX_MINUTES`, default 60 min; `batchTimeoutMinutes` w configu wygrywa, gdy ustawione), NIE wliczany w budżet czasu runu - poll checków przestaje wymagać `remainingDurationMs` runu (token budget dalej egzekwowany), a moduł budżetu odejmuje czas fazy checks od konsumpcji duration. Lifetime sandboxa przy tworzeniu = jobTimeoutMs + limit checks (prepare-workspace.ts:372) - inaczej sandbox umrze pod batchem.
- **Zero pasujących checków** = outcome `skipped` (nie `passed`), głośne summary "0 komend wykonanych - żaden wpis nie pasował do zmienionych repo" w Jira/run details; PR przechodzi.
- **Env/sekrety**: config per repo `env?: string[]` (nazwy). Wartości TYLKO z env workera, filtrowane ALLOWLISTĄ operatora (env `PRE_PR_CHECKS_ALLOWED_ENV`, lista nazw); nazwa spoza allowlisty lub nieustawiona = głośny błąd startu batcha ("could not be started"), nie cichy no-op. Wartości podane przez `runCommand env` (unia batcha); wrapper izoluje per repo (kopiuje do pamięci shella, unset między repo). KAŻDA wstrzyknięta wartość scrubowana z outputów per komenda przed persystencją, niezależnie od wzorca nazwy (redaktor po nazwie łapie tylko /(password|secret|token|.../i - DATABASE_URL by przeszło).
- **Raportowanie**: wzbogacić ISTNIEJĄCĄ ścieżkę komentarza porażki (`postFailureReasonCommentStep`, agent.ts:1906-1928) zamiast dodawać drugi komentarz; komunikaty rozdzielone: "Pre-PR checks failed: <repo>: <cmd> (exit N)" vs "could not be started" (setup/env/infra) vs skipped; komunikat bramki czystości nazywa pliki/komendę; diagnose/trace przestają pokazywać wyłącznie `status:"ok"`.
- **Toolchainy**: runtime zostaje node24, zero preinstalacji; presety setup w docs (uv: oficjalny instalator do ~/.local/bin + PATH do WŁAŚCIWEGO pliku profilu: .bash_profile -> .bash_login -> .profile, nigdy nie tworząc .bash_profile; weryfikacja `uv --version`). Edytor /checks ostrzega, gdy komenda w `commands` wygląda na instalacyjną (uv sync, yarn install, pip install...) - należy do `setup`.
- **Fix agent**: bez nowego bloku; weryfikacja e2e brancha na outcome + przykład w docs.

## Assumptions (przyjęte rekomendacje po pre-mortem)

1. `fixCycles` w output = stałe 0; klucz `maxFixCycles` zostaje w schemacie (strict), znika z defaults rejestru i z UI.
2. Per-command timeout: default 10 min (env), override per repo w configu; przekroczenie = wynik "timed out", nie błąd fazy.
3. Katalog wyników kluczowany `commandId` + lockfile; runner odmawia startu na zajętym kluczu (chroni przed AIW-242/AIW-251 - podwójne wykonanie regionu / re-run kroku po śmierci inwokacji).
4. Env: unia batcha przez `runCommand env`, izolacja per repo w wrapperze (pamięć shella, unset między repo); scrubbing wszystkich wartości z outputów.
5. Nowy sekret = env w Vercel + redeploy workera; KOLEJNOŚĆ ROLLOUTU: najpierw release workera z nowym schematem, dopiero potem zapis configu z `env` (stary worker ma `.strict()` i wywali parse configu z nieznanym polem).
6. Raport per komenda: head+tail (heurystyki w sandboxie na pełnym outputcie), do Jiry ogon 2000 znaków.
7. `run_checks` v1 zostaje report-only; jego kontrakt (`results`/`failures`) jest wzorcem dla rozszerzenia kontraktu `run_pre_pr_checks`.
8. Migracja DB niepotrzebna (config = JSON w wersjonowanej tabeli); gdyby jednak - następny wolny numer 0053.
9. Edycja configu w trakcie runu dalej kładzie bramkę `configuration_changed` - udokumentować "nie edytuj w trakcie runu"; zmiana porównania na fingerprint = out of scope.
10. Ceiling fazy checks = PRE_PR_CHECK_BATCH_MAX_MINUTES (default 60 min, `batchTimeoutMinutes` z configu wygrywa) + lifetime sandboxa z zapasem; przekroczenie = partial results + głośny raport, nie "terminated".
11. Stary kształt configu (`commands` bez grup) czytany przez normalizację do `groups.checks`; zapis zawsze w nowym kształcie; historia wersji nietknięta.
12. `run_pre_pr_checks` nie jest przemianowywany w miejscu (deployowane definicje odwołują się do typu bloku po nazwie); generyczność wchodzi nowym blokiem `run_scripts`. Ewentualne wycofanie starego typu = osobna decyzja po adopcji.
13. Nazwa domeny: "Repository scripts" (robocza; ostateczna kombinacja nazw do potwierdzenia z Jakubem).
14. Setup przy workspace liczy się do normalnego budżetu runu (jest krótki względem batcha testów); marker setupu per repo per sandbox, więc resume/nowy sandbox doinstalowuje zamiast padać.
15. Composite: `extends` tylko na poziomie grup (DAG, ekspansja z deduplikacją); komendy nie referencjonują niczego. Lifecycle hooks NIE wchodzą: semantykę "pre-PR" daje wskazanie grup w konfiguracji bramki (odpowiedź na zaparkowane pytanie ze spotkania 21.08).
16. Przywracanie czystości drzewa: snapshot brudu PRZED batchem, restore per plik (`git checkout HEAD --`, kryje też staged) TYLKO dla plików zabrudzonych przez batch; brud zastany zostaje nietknięty i raportowany (bramka pada głośno jak dziś). Grupy naprawcze (np. prettier-fix, przykład Jakuba): per-group `restoreTree: false` zostawia modyfikacje i raportuje w `dirtied`; użyta w bramce = świadome ryzyko głośnej porażki bramki czystości (decyzja z gate'u sceptyka etapu 2).
17. Status grupy liczony po PEŁNYM rozwinięciu (post-extends), wyniki komend współdzielone między grupami po dedupe wykonania; failed wygrywa z timed_out; timeout wymaga exit 124 ORAZ czasu >= ~90% limitu.
