# Repository catalog and dashboard settings

Status: APPROVED by the owner on 2026-09-11, revision 3 (owner decisions: everything that sensibly can be edited from the dashboard moves out of the environment; import suggests script groups and an LLM call suggests the description; script groups move into the repository profile now and the Scripts page is replaced by a Repositories page; one settings store with a Settings page and area panels; an empty catalog keeps today's behaviour with a banner; suggestions run on demand. Two independent skeptic pre-mortems of the same day, twenty findings, every one adopted; see Assumptions). Runs in parallel with the workflow graph package plan (stage 12 of the restructure). Jira: epic AIW-338, ticket to be created.

## Problem

A person setting up AI Workflow decides which repositories the agent may touch by editing an environment variable and redeploying, and cannot tell from the product which features are on, what the limits are, or what the system knows about a repository. Six places hold a piece of repository knowledge (the allowlist, the script groups blob, workflow pins, memory documents, owned branches, the provider directory) and none of them is the repository. About 35 behaviour switches are read straight from the environment, invisible in the dashboard and changeable only by redeploying.

## Solution

The dashboard gains two things. A **Repositories** page lists every repository the deployment knows, each with a description, rules, script groups, memory, relationships and a change history; repositories are added by importing from GitHub or GitLab, and an on-demand suggestion fills in the description, rules and script groups from the repository's own README, manifests and CI files for the admin to review. A **Settings** page shows what is configured and lets an owner or admin change every product-behaviour switch in grouped forms, with every change versioned and attributed; the same switches appear as small panels on the pages they belong to (Memory, Health, Checks). Secrets and deployment wiring stay in the environment and are shown only as present or missing. The Scripts page goes away; its content lives on each repository.

## User stories

1. As an admin I want to import repositories from my GitHub or GitLab installation so that the agent can work on them without an environment change and a redeploy.
2. As an admin I want each repository to carry a description and rules so that the planner selects the right repository and follows the repository's conventions.
3. As an admin I want the system to suggest the description, rules and script groups from the repository itself so that onboarding a repository takes minutes.
4. As an admin I want the script groups of a repository edited on that repository so that editing one repository never invalidates a run on another.
5. As an admin I want to disable a repository so that no trigger, dispatch or expansion selects it, without deleting what the system knows about it.
6. As a user I want a Settings page that shows what is configured and which features are on so that I know what I can use.
7. As an admin I want to change limits, cadences, feature switches and MCP limits from the dashboard so that a change takes effect without a redeploy.
8. As an admin I want every settings and repository change recorded with who changed what and when so that a behaviour change is traceable.
9. As an operator I want a fresh deployment to behave as today until I activate the catalog myself, with a visible banner, and I want a run that is already in flight to finish under the rules it started with.

## Implementation decisions

**Settings registry and store.** A typed registry in the contracts package lists every setting: key, group, type, default, description, whether a change applies to runs already in flight (for every key the workflow body reads, the only allowed value is "next run"), and whether a later plan may override it per trigger. Groups: General (organisation name and slug, default target branch), Capacity (max concurrent agents, job timeout, block concurrency, poll interval), Attachments (max file size, total size, count, download timeout), Features (review phase, leak review, repository memory, organisation memory promotion, routing memory, review ledger, MCP enabled), MCP (public dynamic client registration, audit retention, request and result byte limits, tool timeout, read and mutation rate limits), Checks (default command timeout, forwarded environment allowlist), Harness defaults (agent kind, Claude model, Codex model; harness profiles override per run), Issue tracker (the three column names, a deployment default until triggers own them), Triggers (default rate limit max and window), Repositories (catalog activated, set only from the Repositories page). The store keeps one row per key with a JSON value plus a versions table (key, previous value, new value, actor, reason, timestamp). Writes validate against the registry type and reject unknown keys. The existing settings service module (its runtime, integration and index modules) is rewritten to read the snapshot; no second settings module is created.

**The snapshot is loaded once per entry and passed down synchronously.** The store is asynchronous, the consumers are not: today's accessors return values, not promises, and a silently returned promise would flip a feature on. Every entry point loads one immutable snapshot asynchronously and hands it down: an HTTP handler at request start, a cron tick at its start, the MCP transport per call, and a run through one new `"use step"` at run start that stores the snapshot in the run context, because the workflow body itself reads settings (column names, agent kind, models, job timeout, memory and ledger switches, block concurrency) and a workflow body may read nothing from a database and must see the same value on replay. The accessors change from `accessor()` to `accessor(snapshot)`; no accessor returns a promise anywhere, and a test asserts it for every registry key; the workflow divergence test configuration is part of the consumers' definition of done.

**Resolution order until the environment is gone.** Until the cleanup stage, a missing row resolves to the environment value when the variable is set, and only then to the registry default; after the cleanup stage removes the environment parsing, the registry default is the fallback. A deployment with a non-empty environment and an empty table therefore behaves exactly as today. Seeding runs as a data migration in the same build step that already runs the schema migrations (idempotent insert, do nothing on conflict), never on a request path; the Settings page shows, per group, whether a stored row exists. After the cleanup stage, a set `AGENT_ALLOWED_REPOS` or any migrated variable fails environment validation with a message naming the dashboard page that replaced it, so a new tenant deployed from an old runbook cannot silently run open.

**Repository catalog.** A repositories table: provider, path, display name, default branch, description (markdown), rules (markdown), relationships (list of catalog ids with a free label), enabled flag, source (imported, manual, seeded, migrated), timestamps. A repository profile versions table records every change to description, rules, relationships and script groups with actor and reason. Script groups move from the global versioned blob into the profile: each repository's profile version carries its groups and its gate group selection. The catalog service exposes list enabled, get, is enabled, upsert, set enabled, list versions, and the import and suggestion entry points; every database access goes through the repositories tier, so the database client fence stays at zero. Saving a profile writes the profile row and its version row in one statement (a data-modifying CTE); the import commit is one multi-row insert with do nothing on conflict. The consecutive-writes gate stays green without a new allowlist entry.

**Activation, not row counting, ends the bridge.** While the catalog is not activated, the catalog answers "enabled" for every accessible repository and reports the bridge, which the dashboard shows as a banner on Repositories and Settings ("catalog not activated, the agent sees everything the installation sees"). Activation is one explicit action on the Repositories page whose dialog names every repository that currently holds an active run claim and is not enabled, so the admin sees what the next dispatch will stop selecting; no migration and no import ever flips it. The seed migration sets activated to true exactly when the allowlist variable is non-empty (that deployment is restricted today) and imports as enabled seeded rows every entry of the variable and every repository pinned by any stored definition, published or draft (pins grant access today); the script groups migration creates one row per repository the blob names, enabled only if that repository is already enabled by the seed, otherwise disabled with its profile kept. A production count after the migration on a copy of the database, compared with the variable, is part of the catalog stage's definition of done.

**The catalog is the only grant; pins select, they no longer extend.** After activation a pin selects among enabled repositories and a pin on a repository with no row or a disabled row is reported at save and publish (the MCP field `repositoriesOutsideAllowlist` is renamed `repositoriesNotEnabled` with the same shape; the contract snapshot is regenerated in the services consumers stage).

**The decision is made per run, outside the steps, and stays synchronous.** The services tier (dispatch, manual dispatch, webhook handlers, MCP authoring) loads one catalog snapshot per invocation and feeds today's synchronous predicate with it; the re-export barrier in the dispatch services is kept as the single import path. Workspace preparation records the list of enabled repository keys in the run context; the expansion protocol and every later step (publisher, promotion, pull requests, comments, fetch context) filter against that carried list synchronously, so no step and no loop performs a database read per element and a run finishes under the rules it started with. No module reachable from the workflow isolate reads the catalog (the structural schema module in particular). The allowlist module and its environment reader are deleted and listed in the resurrected-paths gate.

**Script groups migration and the Finalize gate.** A data migration copies the current script groups blob into one profile version per repository it names (version 1, actor "migration"). The workspace gate carried across steps keeps `configurationVersion` and `fingerprint` forever and gains an optional `repositoryVersions` field (repository key to profile version); the block contract in the block registry declares the new field optional, the blocks catalog is regenerated, and the recovery of the gate from step checkpoints accepts both shapes indefinitely (the same way `fixCycles` was added). The profile versions are recorded at the moment the checks pass (where the successful gate is recorded today), never earlier, so the invariant "the version the checks ran under equals the version now" survives; a repository added by expansion after that point records its version when its checks pass. Every reader of the check configuration (the checks blocks, the run-checks block, the check configuration service, the failure reporter) reads per-repository profiles in the same stage. No `"use step"` function changes name or file; new data enters as optional parameters. Whether deployed definitions need a resync migration is decided by the catalog stage's reviewer from the regenerated catalog diff.

**Import and suggestions.** A repository profile source interface with a GitHub and a GitLab adapter returns, for one repository: default branch, provider description, the first part of the README, the manifest files it recognises (package manifests, lockfile names), the CI definitions, and languages. The provider directory stays where it is (the existing repositories route with its one-minute cache, used by the editor's repository picker) and feeds the import screen only; the catalog has its own route prefix. The import flow lists the installation's repositories, the admin ticks the ones to add, rows are created disabled or enabled per the admin's choice, and no suggestion runs automatically. The suggestion runs on demand for one repository: the source bundle (about 32 KB at most) goes to one LLM call through the existing LLM infrastructure with the cheapest model of the default harness profile and an explicit timeout of 90 seconds; the worker route and the dashboard route declare a maximum duration of 120 seconds; a second click while a suggestion is in flight for the same repository joins the in-flight call instead of starting another; the answer is validated against a schema and a malformed answer is an error with nothing saved; the result is a proposal shown next to the current values and nothing is written until the admin saves. Every suggestion call is recorded in a suggestions table (repository, actor, model, usage, cost, outcome, timestamp) so the cost page can show it without a run id.

**Dashboard.** Settings page: a setup overview at the top (issue tracker and VCS connected, catalog activated and repositories enabled with a link, features on and off, MCP state, memory state, secrets present or missing, stored rows per group), then one form per group with the description of each setting and its history. Area panels: the Memory page shows the memory switches, the Health page shows the setup overview, the Checks area shows the checks defaults and links to Repositories instead of Scripts. Repositories page: a list with description, enabled state, script group count and last change; the activation banner and dialog; an entry with tabs Overview (description, default branch, relationships), Rules, Scripts (the existing group editor bound to this repository), Memory (the two per-repository documents), History; buttons Import from provider and Suggest from repository, with pending, timeout, in-flight and malformed-answer states. The Scripts page and its dashboard route are removed; a redirect points to Repositories.

**HTTP contract and roles.** The worker exposes settings read and update, and under a repository catalog prefix: list, get, upsert, set enabled, activate, versions, import preview, import commit and suggest; request and response schemas live in the contracts package next to the existing dashboard contracts. Reads are open to every dashboard role; writes require the owner or admin role through two new predicates in the dashboard roles contract (edit settings, manage repository catalog) enforced by the dashboard actor guard; a member gets 403 on writes and 200 on reads, asserted by tests.

**Migrations are serialized.** Four stages carry a migration and they merge in this order with fixed numbers: settings (0059), catalog (0060), suggestions (0061), cleanup (0062). No other stage adds a migration. Stages may start in parallel; the second to merge rebases its journal entry.

**File scopes are lists, not globs, and overlapping stages never run at once.** Each stage's scope below is a list a script can check; two stages start in parallel only when their lists are disjoint. The engine wave owns every engine file that both the settings consumers and the catalog consumers would otherwise touch.

## Out of scope

- Per-trigger overrides of column mapping and repository scope (roadmap P1, trigger-owned configuration; the registry only marks which settings may be overridden later).
- MCP tools for the catalog and settings (a follow-up once the HTTP contract has been used by the dashboard for a while).
- Moving secrets, provider identity, database and auth URLs, the bot account identity, or the pricing endpoint out of the environment.
- Repository setup commands and sandbox runtimes (roadmap P0, repository environments); the profile leaves room for them but this plan adds none.
- Memory content editing beyond linking the existing documents on the repository entry.

## Assumptions

1. Build-time seeding sees the deployment's environment variables (Vercel exposes them to the build step, where the schema migrations already run); the seed is idempotent and a failed build stops the deploy, so a half-seeded production cannot exist. Skeptic A9.
2. The workspace gate shape change is additive, both fields stay forever, recovery accepts both shapes indefinitely, and nothing is removed from the block contract later. Skeptic A5, B4.
3. The bridge is an explicit activation flag; no migration or import flips it; a run in flight is unaffected because it carries its enabled list from workspace preparation. Skeptic A2, A4, B1.
4. The suggestion call is bounded to about 32 KB of bundle text, 90 seconds and one response; a repository without a README or manifests still gets a proposal from provider metadata alone. Skeptic A8.
5. The Scripts page removal is acceptable because every field it edited (groups, extends, gate groups) is on the repository entry; the Checks page link, the Arthur runbook and the repository scripts documents are updated by the stages that own them. Skeptic A7.
6. Harness defaults in the registry only replace the environment fallback; harness profiles keep deciding the model per run.
7. Every multi-row write is one statement (the profile save CTE, the import insert) and the consecutive-writes gate proves it without a new allowlist entry; no engine or services file imports the database client, so the fence stays at zero. Skeptic A6, B8.
8. The provider directory route keeps its name and cache and is not the catalog; the catalog routes have their own prefix. Skeptic A7, B9.
9. Pins stop extending access; the seed imports pinned repositories so no published definition loses a repository at migration. Skeptic A1.
10. The settings consumers work is a synchronous-to-snapshot conversion with real risk, so it carries a skeptic and TDD and runs in waves with disjoint file lists. Skeptic A3, B3, B10.
11. The single owner account on a fresh deployment can complete onboarding because writes accept owner or admin. Skeptic A10.
12. A new tenant (for example the Arthur deployment, a separate database) upgrading after the cleanup stage starts in the bridge with the banner, and a set allowlist variable fails validation instead of being ignored. Skeptic B2.
13. Profile versions are recorded when checks pass, not at workspace preparation; the enabled list is recorded at workspace preparation; the two records serve different invariants. Skeptic B6.
14. No `"use step"` function is renamed or moved; new inputs are optional parameters and the dual-shape recovery makes a drain unnecessary; the reviewer of the catalog stage confirms this with the divergence configuration. Skeptic B5.
