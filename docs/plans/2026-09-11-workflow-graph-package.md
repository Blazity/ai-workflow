# Stage 12: the workflow graph as a package

Successor plan to [docs/plans/2026-09-09-architecture-restructure.md](2026-09-09-architecture-restructure.md), row 12. Owner decisions of 2026-09-11: run right after stage 11 closes; dashboard forms generated from block manifests are out (a separate product plan); block manifests stay in `apps/worker/src/engine/blocks`, the package validator receives its block data as parameters; the package imports only `@shared/contracts`, `@shared/conditions` and zod (ADR-001 unchanged). Architecture review of 2026-09-11 (candidates 1 to 8, report in the advisor's notes) shapes the stages; the skeptic pre-mortem of the same day (ten findings, all folded in below) corrected the block-data seam, the policy set, the test placement and the stage cuts.

## Problem

The rules that say what a workflow definition is, whether it is valid, how its blocks are scheduled and how values flow between them live in `apps/worker/src/workflow-definition`, next to persistence, prompt drift checks and harness runtime code. Nothing outside the worker can use them, so the dashboard round-trips to the worker for every validation, the same graph analysis runs five times per request, six callers repeat the same validate-then-map sequence, and a pure rule cannot be tested without booting the worker's module graph (2046-line `schema.ts` pulls every block module, the MCP tool catalog restates the graph limits because importing them costs the whole engine).

## Solution

A workspace package `packages/workflow-graph` (consumed as `@shared/workflow-graph`, flat files, no build step, `node:test`) owns the pure graph logic: the v2 definition schema and its structural validation, bindings and available values, the scheduler, the interpreter, layout canonicalization, templates and workspace access rules. It depends only on `@shared/contracts`, `@shared/conditions` and zod; everything it needs from the worker (block parameter schemas, resolved block contracts) arrives as data through its interface. The worker keeps deployment validation (harness profiles, prompts, schedule occurrences, repository script groups, database state) and calls the package through one entry per validation policy. Behaviour is identical before and after: the same definitions validate, the same issues are reported, the same runs schedule the same blocks in the same order.

## User stories

1. As a worker maintainer I want the graph rules in one package with one interface so that a validation or scheduling bug is fixed in one place and proven by a test that runs in under a second without the worker.
2. As a dashboard maintainer I want the structural rules to be importable without the worker so that a later plan can decide whether the editor runs them locally; that plan has to supply a block contract resolver, because block availability is derived from the worker's environment and model catalog and the browser cannot reproduce it.
3. As a reviewer I want the gates to reject a package import of worker code or of `@shared/harness` and `@shared/prompts` so that the package stays pure by construction.
4. As an operator I want no change in what runs on production: the same step files, the same step identities, the same definitions accepted and rejected.

## Implementation decisions

- Package layout mirrors `packages/contracts`: flat files, `index.ts` as the only public entry, `package.json` with `exports["."]`, a `test` script on `node:test`, `tsconfig.json` copied from `packages/conditions`. The gate `tiers.json` gains the package edge `workflow-graph -> contracts, conditions`; knip gets the workspace; `package-contracts` and `deps-consistency` cover it.
- Block data as parameters, not context. A block contract is a function of the node's own params (`resolveWorkflowBlockContract(type, params, context)` derives the output schema, the binding schema and the availability from `params.providers`, `params.on` and the custom output schema), so the package receives a resolver `(type, params) => WorkflowBlockContract`, built once per request by the worker from the registry, the environment and the model catalog; the per-type table built from defaults stays what it is today, presentation data. The package also receives the complete per-type map of block parameter schemas, composed in the worker (`engine/definition`) from the twenty worker-local zod configurations and the fifteen manifest params exactly as `schema.ts` composes them now, with the `satisfies Record<WorkflowBlockType, ZodTypeAny>` exhaustiveness check kept at the composition site and a test that every block type has a schema. `PROMPT_SLOT_NAME_PATTERN` and `repositoryScriptGroupNameSchema` move to `packages/contracts`. The package never imports a manifest, `infra/llm-provider`, `@shared/prompts` or the generated executors.
- One analysis pass. Available-values analysis of a definition is computed once and handed to every consumer of one validation request; the duplicated preamble inside `available-values.ts` is deleted.
- The `schema.ts` split line is structural versus deployment. Structural (schema, graph issues, size limits, bindings, ports) goes to the package; deployment (harness profile existence, prompt references, schedule occurrence rules, repository script group names) stays in the worker under `services/workflow-definitions`. The MCP tool catalog keeps its restated limits: its transport path must not load every block module, `tool-catalog.test.ts` already asserts the constants match, and the package barrel is not imported there.
- One validation entry per policy. The package exports `parse` (schema parse with the deterministic stored-shape upgrades that `z.preprocess(normalizeV2AgentProfileConfiguration)` performs today, no issue checking: the repository read path keeps using exactly this), `draft` (structural issues only), `deploy` (structural issues plus environment availability through the resolver) and `run-load` (`deploy` without the environment availability check, what `definition-step.ts` passes as `checkEnvironmentAvailability: false` today); a stored snapshot validates with `deploy`, there is no separate lenient policy. Each policy composes parse, structural validation and one issue de-duplication. The worker's deployment validation wraps `deploy` and adds the worker-only checks. The never-read `allowLegacyCompatibility` option and its stale comment are deleted; the DoD proves a legacy stored row round-trips unchanged through `parse`.
- The interpreter is split by concern: interpretation of values and expressions (package) versus execution-error typing and run budget (worker, `engine/helpers`). The scheduler's `executionError` calls use a package-owned error shape declared in `packages/contracts`.
- The transform step inversion: the package exposes a pure transform that takes an optional async regex evaluator; the worker's `engine/steps/transform-regex-step.ts` (a `"use step"` file, not moved, not renamed) stays the only place that loads `re2-wasm`, and the engine passes it in.
- Dead code is drained before anything moves: the unused v1 binding validator in `bindings.ts`, the `layout.ts` duplicate of `packages/contracts/workflow-layout.ts`, the pure re-exports in `stored-definition.ts`. Nothing dead becomes package interface.
- The worker directory `apps/worker/src/workflow-definition` is deleted at the end: the persistence, drift and harness runtime modules are re-homed by their imports (`db/repositories`, `services/workflow-definitions`, `engine/helpers`), the scenario test harness moves under `engine/tests`, and `scripts/gates/no-resurrected-paths` lists the directory.
- Tests stay on vitest in the worker. The suites of the moved modules (6389 lines: `v2-scheduler.test.ts` 2184, `schema-v2.test.ts` 1868, `available-values.test.ts` 894 and the rest) use `expect`, `toMatchObject`, `it.each` and the 15 s timeout, none of which `node:test` offers without weakening assertions; they stay where they are, import `@shared/workflow-graph`, and the `packages/conditions` precedent applies. The package's own `node:test` script covers only its public entry (one smoke test per exported policy and function), and `verify:changed` maps a package change to the worker suites that import it.
- Freeze: no `"use step"` or `"use workflow"` file moves or is renamed; the step set is compared to the stage base at every gate; prod health on the exact merge SHA plus one real run on the QA project after every merged stage that changes runtime code.

## Out of scope

Dashboard forms from manifests; any dashboard file; moving manifests or executors; the drain protocol (no step file moves); `@shared/harness` or `@shared/prompts` as package dependencies; auto-layout (none exists, layout means persisted coordinates).

## Assumptions

- A1. Leaving the moved modules' suites in the worker keeps their coverage intact; the package smoke tests plus the `verify:changed` mapping are enough to make a package change run the right suites.
- A2. `json-schema.ts` (ajv) stays in the worker; nothing structural in the package needs ajv. If a structural rule turns out to need JSON Schema validation, it takes a validator as a parameter.
- A3. The block contract resolver needs the environment and the model catalog but no stored definition state; if a structural rule turns out to read stored state, it is deployment validation and stays in the worker.
- A4. The Nitro and Workflow DevKit builds bundle the new package like `@shared/conditions` (stage A3 spike, `build:ci` proves it before merge, a real prod run proves it after).
- A5. Performance is neutral or better (one analysis pass instead of five).
