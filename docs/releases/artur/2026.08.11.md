# AI Workflow — 2026.08.11

## Highlights

This release ships the System health screen and closes the loop on automatic check fixes. The dashboard can now tell you, on demand, whether every integration this deployment depends on actually works with the credentials it holds, and it remembers the last result. Automatic check-fix runs finish cleanly on the commit they pushed, and a reviewer's request for changes can no longer be dismissed as "already resolved".

## What's new

- A System health screen in the dashboard, for administrators. Press Scan and the worker verifies the database, Jira, the GitHub App, GitLab, single sign-on, email delivery, Slack, the configured agent provider and the remote tool contract, each with its own live check, and reports every one as live, down, degraded or not configured. Webhooks are verified for real: GitLab receives a test delivery, the GitHub App's webhook configuration and latest delivery are read back, and Jira's webhook registration is checked when the token allows it. Every row names the environment variables it depends on; secret values never appear.
  <!-- sources: 329,335 -->
- Nothing runs in the background. A scan happens only when you press the button, and the screen opens with the stored result of the last scan and the time it ran, so visiting the page never calls your providers on its own.
  <!-- sources: 331,337,338 -->

## Improvements and fixes

- An automatic check-fix run now completes on the commit it pushed itself. Previously the run repaired the branch and pushed it, then failed with a stale-commit error at the last two steps, so the pull request ended up fixed and green with nothing said about it and the run marked as failed. Both places that compared commits now accept the run's own push, while a push from anyone else still stops the run.
  <!-- sources: 324,326 -->
- When a reviewer has asked for changes on a pull request, the planning agent no longer closes the ticket with "already resolved, no code changes needed". It plans the requested changes, retries once if it refuses, and fails visibly rather than reporting a success nobody asked for.
  <!-- sources: 325 -->

## Do you need to do anything?

No action is required. The System health screen appears in the dashboard navigation for administrators; press Scan once after the upgrade to see the state of your integrations.

## Known limitations

A scan is a snapshot: the screen shows the last stored result until someone presses Scan again. Pre-PR check commands still do not report which command failed, only that the batch failed, so a red pre-PR gate needs the run log to diagnose.
