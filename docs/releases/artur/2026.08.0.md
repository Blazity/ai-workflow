# AI Workflow — 2026.08.0

## Highlights

The headline of this release is a completely new visual workflow editor: you compose how the agent works from connected blocks, with branching, parallel steps, first-class prompts and output schemas, guided migration and visual replay of runs. Alongside it: versioned Harness Profiles, runs that span multiple repositories, agent memory, and automated review cycles after the pull request. Underneath, a long list of reliability fixes makes run statuses truthful and the platform steadier under load.

## What's new

### A new visual workflow editor

Workflows are now built on a canvas of connected blocks with typed data flowing between them: triggers for Jira tickets and GitHub or GitLab pull requests, a Branch block with plain AND/OR conditions and typed outcomes, a Transform block with seven ready-made data operations, and branchable Run Checks and Pre-PR Checks. Workflows can fan out into parallel steps and join the results back together. Prompts are written in a rich editor with validated Prompt Slots and drag-in content from the prompt library, with an effective-prompt view that shows exactly what the agent receives; each agent's output shape is defined in a schema editor, visual or raw JSON Schema. Data is wired through one searchable picker with live compatibility checks, values drop into prompts as inline chips, and everyday editing is comfortable: multi-select, copy and paste across workflows, 100-step undo, keyboard support. Owners can also trigger a deployed workflow manually with a ticket key or PR link.

- Provider and repository scope moved into a compact Source scope bar with a dedicated edit dialog.
  <!-- sources: 177 -->

### Trust, migration and replay

Workflows are validated while you edit and again before deploy, with invalid blocks flagged in place. Any run can be replayed visually: the exact path taken and each step's inputs and outputs, live while it runs, scrubbed of secrets and kept for 30 days. Existing workflows keep running unchanged: a guided v1-to-v2 migration previews the conversion, keeps the current version live until you deploy, and preserves each agent's model. Loop iterations and parallel reviewers are isolated from each other, runs that fail to start are auto-recovered within minutes, and duplicate runs are prevented.

- Releases to your environment are now prepared, reviewed and published through an automated pipeline; these notes are its first product.
  <!-- sources: 193 -->

### Harness Profiles

A Harness Profile pins the exact combination an agent runs with: provider, tool version, model, capability settings and skills. Published versions are immutable, so agent behaviour never drifts silently. A dedicated studio manages profiles end to end (version history, restore, duplicate, archive, usage tracking), skills import from GitHub in bulk pinned to an exact commit, and the model picker reflects live, auto-refreshed discovery of what the pinned tooling actually supports.

### Multiple repositories

- One ticket can span several repositories: the agent picks the right one, asks with ranked candidates when unsure, pulls in discovered dependencies, and opens one PR per changed repository.
  <!-- sources: 159 -->
- Pin up to 8 repositories (GitHub and GitLab together) to a workflow; the "which repository" question disappears.
  <!-- sources: 170 -->
- Every PR and MR a run opened is linked from the run, in the dashboard, trace view and Slack.
  <!-- sources: 188,189 -->

### Agent memory

- The agent's memory moved out of your repositories into the platform, with a browser in the dashboard; no more helper files in your codebase. Runs can also mix GitHub and GitLab repositories.
  <!-- sources: 166 -->
- With memory on, the agent keeps per-repository and per-organization knowledge (commands, layout, lessons from past runs), so later runs start smarter; off by default, admins can browse and delete entries.
  <!-- sources: 182 -->
- Everything the agent publishes is scrubbed so internal bookkeeping never leaks into PR bodies, reviews or questions.
  <!-- sources: 190 -->

### Reviews after the pull request

Human review comments now reach and steer the right run: one review with many inline comments starts exactly one follow-up, formal "Request changes" reviews are detected reliably on GitHub and GitLab alike, moving the ticket back to the AI column applies the feedback, and the agent never reacts to its own comments. Two new editable templates round this out: "Reviewed ticket" (three parallel AI reviewers, a verdict branch, up to three automatic fix retries) and "Post-PR review" (reacts when a PR is ready or updated, posts one combined review, reports pass or fail as a real provider check).

## Improvements and fixes

The common theme: statuses tell the truth.

- Finishing runs are no longer cancelled by Jira board automation, and completed runs are recorded as completed.
  <!-- sources: 148,173 -->
- Failed and blocked runs show their real, specific reason, and steps are never silently dropped.
  <!-- sources: 167 -->
- Clarification handling is sturdier: parked runs stay alive and replies match short names and typos (both delivered to your environment earlier as hotfixes, now part of the mainline release).
  <!-- sources: 157,184 -->
- An outage at one provider (for example GitLab) no longer disturbs runs on the other.
  <!-- sources: 175 -->
- The implementation agent no longer self-publishes changes or mislabels failures.
  <!-- sources: 183 -->
- Production stress-test hardening: a working Approvals page, no silently skipped tickets, full error text, no phantom "running" runs, plus a second review pass over all of these fixes.
  <!-- sources: 192,194,195 -->

## Do you need to do anything?

No. Existing workflows keep running unchanged, migration to the new editor is optional, and agent memory stays off until enabled for your environment.

## Known limitations

Visual replay covers runs started after this release. Agent memory rolls out gradually and can be switched off at any time.
