# AI Workflow — 2026.08.0

## Highlights

This is the largest AI Workflow update to date. The centerpiece is a completely new visual workflow editor: instead of a fixed pipeline, you now compose how the agent works on a canvas of connected blocks, with branching, parallel fan-out, first-class prompt authoring, explicit output schemas, data transformations, guided migration from existing workflows, and visual replay of past runs. Around it, the platform gained Harness Profiles (versioned configurations that pin exactly which AI model, tooling and skills every workflow runs with), support for tickets that span several repositories at once, a memory that lets the agent learn your projects over time, and automated review cycles that continue after a pull request is opened. A long list of reliability fixes rounds this out: run statuses now tell the truth, failures come with real reasons, and an outage at one code-hosting provider no longer disturbs unrelated work.

## What's new

### A new visual workflow editor

Workflows are now built on a canvas of connected blocks, so you can see and shape exactly how a ticket travels from trigger to pull request.

- Workflows are assembled from blocks with typed data connections: triggers (Jira ticket, GitHub or GitLab pull request), a Branch block with plain condition lists, AND/OR logic and typed outcomes, a Transform block with seven ready-made data operations (format, trim and replace text, convert between text and numbers, parse JSON, build objects) that report success or failure you can branch on, and explicit Run Checks and Pre-PR Checks blocks whose verdicts are part of the flow.
  <!-- sources: 136,156 -->
- Workflows can fan out into parallel steps and join the results back together, so independent parts of a task (for example several reviews) run at the same time instead of one after another.
  <!-- sources: 136,172 -->
- Prompts are written in a continuous editor with validated Prompt Slots and inline, highlighted references to workflow data; ready-made content can be dropped in from the prompt library, and an effective-prompt view shows exactly what the agent will receive, including where each instruction comes from and which one takes precedence.
  <!-- sources: 136,155 -->
- Structured outputs get a dedicated schema editor, available both as a visual builder and as raw JSON Schema that keeps your formatting, so the shape of each agent's output is explicit and validated.
  <!-- sources: 135,136 -->
- Wiring data between blocks happens in one searchable picker of values from previous steps and run info, with live compatibility checks; the same values drop into prompt text as inline chips, several values can be collected into a list input, and the Open PR block's outputs (links and numbers) are always available to later steps.
  <!-- sources: 155,169 -->
- The canvas is comfortable to edit: multi-select with group dragging, copy and paste between workflows, 100 steps of undo and redo, adjustable connection routing, and keyboard-friendly editing with confirmation before delete.
  <!-- sources: 150 -->
- Owners and admins can trigger a deployed workflow manually straight from the canvas by entering a ticket key or a pull request link; preflight checks run first and a direct link to the started run appears on success.
  <!-- sources: 152 -->
- Choosing which providers and repositories a workflow works with now lives in a compact Source scope bar with a dedicated edit dialog, including repository search and clear warnings, without shifting the canvas around.
  <!-- sources: 177 -->

### Workflows you can trust, migrate and replay

- The editor validates workflows continuously and again before deploy: invalid blocks are outlined in red with a precise explanation, so configuration mistakes are caught while editing instead of failing later at runtime.
  <!-- sources: 135,154 -->
- Every run can be replayed visually: a timeline of the exact path the run took, with the inputs and outputs of each step and live updates while it is still running. Replay data is automatically stripped of credentials and personal data and kept for 30 days.
  <!-- sources: 149,178,181 -->
- Existing workflows keep running unchanged. A guided migration previews the converted version, reports anything that needs attention, keeps your current workflow live until you explicitly deploy the new one, and preserves each agent's original model choice.
  <!-- sources: 153,158 -->
- Loops and parallel steps are safer: each loop iteration only sees its own carried values, and parallel review agents work in isolated read-only workspaces so they cannot disturb each other.
  <!-- sources: 172 -->
- A watchdog detects workflow runs that failed to start and recovers them within minutes, and repeated dispatch attempts can no longer create duplicate runs.
  <!-- sources: 168 -->

### Harness Profiles: versioned agent configurations

Harness Profiles make the "who exactly does the work" part of a workflow explicit and auditable, instead of an implicit setting.

- A profile pins an exact combination of AI provider, tool version, model and capability settings (reasoning effort, verbosity and more) together with a set of skills; published versions are immutable and workflows reference an exact version, so agent behaviour never drifts silently.
  <!-- sources: 147,171 -->
- A dedicated studio in the dashboard manages profiles end to end: browse and search them, inspect and restore previous immutable versions, duplicate and archive profiles, and see which workflows use a given version (versions in use cannot be deleted).
  <!-- sources: 160 -->
- Skills (reusable instruction bundles for the agent) are imported from GitHub repositories in a guided Source, Discover, Review flow, pinned to an exact commit; bulk imports of dozens of skills complete in seconds.
  <!-- sources: 161,162 -->
- The model picker is driven by live capability discovery of the pinned tooling, refreshed automatically in the background, and offers the full model range with the settings each model actually supports.
  <!-- sources: 185,187 -->

### Work across multiple repositories

- A single ticket can now be researched and implemented across several repositories in one run: the agent picks the right repository from clear signals, asks a short clarification question with ranked candidates when it is genuinely unsure, pulls additional repositories in when it discovers a real dependency, and opens one pull request per repository that actually changed.
  <!-- sources: 159 -->
- Repositories can be pinned to a workflow (up to 8, GitHub and GitLab together), so every ticket on that workflow starts from the right codebases and the "which repository" question disappears.
  <!-- sources: 170 -->
- Every pull request and merge request a run opened is linked from the run itself, in the dashboard, in the trace view and in Slack, with compact repository labels that stay readable even for multi-repository runs.
  <!-- sources: 188,189 -->

### The agent remembers your projects

- The agent's working memory moved out of your repositories into the platform: no more helper files in your codebase, with safeguards that keep it that way, plus a read-only memory browser in the dashboard. Runs can also mix GitHub and GitLab repositories in one task.
  <!-- sources: 166 -->
- With memory enabled, the agent retains what it learns per repository (build and test commands, project layout, lessons from past runs) and per organization, so later runs start smarter instead of rediscovering the same facts; admins can browse and delete entries, and everything sits behind switches that default to off.
  <!-- sources: 182 -->
- Everything the agent publishes (pull request descriptions, review comments, clarification questions) is scrubbed so internal platform bookkeeping never leaks into customer-facing text, and stored memory content is kept clean and relevant.
  <!-- sources: 190 -->

### Automated reviews after the pull request

- Human review comments on an agent's pull request now reach the right run and steer it: one review with many inline comments starts exactly one follow-up run, formal "Request changes" reviews are detected reliably on GitHub and GitLab alike, moving the ticket back to the AI column applies the feedback, and the agent never reacts to its own comments.
  <!-- sources: 165 -->
- A new editable "Reviewed ticket" workflow template runs three AI reviewers in parallel, branches on the verdict, and retries fixes up to three times before failing explicitly.
  <!-- sources: 174 -->
- A new editable "Post-PR review" template reacts when a pull request becomes ready or is updated, posts one combined review with inline findings, and reports pass or fail as a real GitHub or GitLab check, superseding itself when a newer commit lands.
  <!-- sources: 176 -->

## Improvements and fixes

This release also closes a long list of reliability gaps found by exercising the platform in production. The common theme: statuses tell the truth.

- Runs that were just finishing are no longer cancelled by Jira board automation moving the ticket, and completed runs are recorded as completed instead of blocked or cancelled.
  <!-- sources: 148,173 -->
- Failed and blocked runs show their real, specific reason; workflow steps are never silently dropped, and stale statuses no longer linger in the dashboard.
  <!-- sources: 167 -->
- Workflows with an answered clarification no longer stay locked, which used to block further plan approvals.
  <!-- sources: 191 -->
- An outage at one code-hosting provider (for example GitLab) no longer disturbs runs that only involve the other; transient errors are retried and hard failures clearly name the affected provider.
  <!-- sources: 175 -->
- The implementation agent no longer attempts to publish its own changes (a later step with proper credentials handles that) and failures are no longer mislabeled as provider or authentication errors.
  <!-- sources: 183 -->
- Reviews on pull requests authored by the platform itself now complete correctly: where the provider forbids self-approval, the review is posted as a neutral comment while the true verdict is still recorded and reported by the check.
  <!-- sources: 180 -->
- A rejected AI review now routes to the request-changes path with its findings intact instead of failing the whole workflow and cancelling other reviewers.
  <!-- sources: 179 -->
- A production stress test led to a final round of hardening: plan approvals are handled correctly with a working Approvals page, new tickets can no longer be skipped silently, error messages keep their full diagnostic text, and the dashboard no longer shows finished runs as still running.
  <!-- sources: 192,194 -->

## Do you need to do anything?

No. The update is applied for you and existing workflows keep running exactly as before. Moving a workflow to the new editor is optional and guided, and new capabilities such as agent memory stay switched off until enabled for your environment.

## Known limitations

Visual replay is available for runs started after this release; older runs show "Not captured". Agent memory and organization-wide learning are rolled out gradually and can be switched off at any time.
