- GitHub is now an integration. Connect it on the Integrations page or keep the environment variables you already have; either way the App keeps posting to the same webhook URL and nothing changes at GitHub's end. With this, version control has no built-in provider left at all: which provider serves a repository comes from the repository record, and a deployment can ship with GitHub and no GitLab, or the reverse, without the absent one showing up anywhere.
- Pasting the App's private key into the form works. It used to want base64 specifically, and a `.pem` file pasted in whole was quietly turned into rubbish that saved cleanly and failed hours later with a message about a bad key. Both forms are accepted now, and a value that is neither is refused before the connection goes live, with a sentence saying which two were expected.
- The Integrations page checks the App itself: whether GitHub still accepts the key, whether the installation still exists and still grants repositories, whether the App subscribes to the events this product needs, and what GitHub's own delivery log says about the last delivery, including that a 401 there means the webhook secret does not match. An installation removed at GitHub's end no longer reads as connected merely because the credentials are still valid.
- A failed check reported by a GitHub App that does not publish a slug used to bind to nothing, so the autofix path went silent on it and the trigger was recorded only as a stale head. Fixed.
- A push to a pull request by the automation account is now judged the same way on both providers, against the exact commit a run published rather than the name on the push. A push by that account to a pull request no run of ours owns triggers a workflow again, as it did before the last release.
- Two startup errors became page rows. A deployment with half its GitHub credentials set, or with the App configured and no webhook secret, used to refuse to boot; it now boots and says so on the Integrations page, naming the variable to set.
- Adding a version control provider no longer means editing this product. A repository's provider, the shape of its paths, the links that belong to it and the account it comments as all come from what the integration declares.
- When this deployment is at its run limit, a provider webhook is answered 202 with `at_capacity` instead of 503. A 5xx bought nothing at GitHub, which never redelivers a failed delivery by itself, and at GitLab a few consecutive failures switch the webhook off, which loses every later event rather than this one. Read the consequence before you rely on it: the delivery now shows as SUCCESSFUL in the provider's log, so nobody will redeliver it by hand, and nothing re-dispatches an at-capacity delivery on its own. The reason is in the response body the provider stores, and the run that never started exists nowhere else. A custom webhook endpoint still answers 503, because its caller has no delivery log and retrying is what we want from it.
