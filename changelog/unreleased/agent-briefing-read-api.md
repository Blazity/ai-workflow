- The API and MCP serve what an agent was sent: a run's sends with their briefings, each section's text page by page, its parts and their origins, the repositories the send described, the sources the prompt could not resolve, and what the run's capture did with the rest, so "eleven sends, two refused" is readable without opening anything. A dashboard and an MCP client read the same bytes.
- Two reads join them: `work_scope.get` returns a subject's repository questions as rounds when a client asks for them, off unless asked for so a client that has been calling the tool keeps today's answer, and `workflows.node_briefing` answers what one block of a definition last sent, from whichever run and whichever version produced it, or the reason there is none.
- `runs.briefing` rides the ordinary read scope, the same one `runs.logs` has always had, so no new permission was created and nobody's grant was widened. What that permission returns is wider: a briefing carries the text of the prompt itself, which holds ticket bodies, `AGENTS.md` and the memory a run was given. Who can read one, and how to narrow or stop a token that can, is in `docs/runbooks/reading-an-agent-briefing.md`.
