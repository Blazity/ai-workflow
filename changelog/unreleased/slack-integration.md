- Slack is now an integration, and messaging is something a workflow asks for rather than a product it names. It has its own card on the Integrations page, its own checks on System health, and connecting it unlocks the messaging blocks everywhere at once. A deployment configured through `CHAT_SDK_SLACK_TOKEN`, `CHAT_SDK_CHANNEL_ID`, `SLACK_SIGNING_SECRET` and `SLACK_ALLOWED_USER_IDS` keeps working with nothing to change, the `/ai-workflow` command answers at the same address, and the thread each ticket already has is the thread it keeps.
- A bot token saved without a channel used to connect and then drop every message in silence. The two are required together now: the card says which value is missing and nothing pretends to be connected.
- "Send Slack message" is now "Send message" and works through whichever messaging integration is connected. Workflows that used it keep running, open in the editor as the new block, and are saved as the new block the next time you publish. Nothing to re-author.
- The block tells the truth about what happened: it reports success only for a message that arrived, and otherwise reports it as skipped with the reason, which a workflow can branch on. Run notifications that are not a block, such as "run started" or "run failed", still stay quiet when they cannot be delivered, because a notification must never change what a run does.
- A deployment with no messaging provider connected still runs its workflows. The blocks that need one say so in the editor and refuse before any work starts, naming what to connect, and the Investigate block reports that it could not read chat messages and reasons from the ticket evidence it has.
- The channel delivery check on System health no longer risks leaving its probe message behind: it retries the cleanup, and when it still cannot delete it, the check says so and gives the date the message would otherwise arrive.
- A slash command whose work failed now answers with the failure instead of leaving you reading "Working on ..." for ever.
- One setting goes away: `CHAT_SDK_BOT_NAME` no longer sets the name messages are posted under, and a deployment that set it will see its Slack app's own name instead. Slack only lets an app post under a different name when the workspace has granted it an extra permission, and sending a name without that permission risks the message not arriving at all, which is worse than the name changing. To choose the name, rename the app in its Slack configuration.
