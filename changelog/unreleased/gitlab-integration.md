- GitLab is now an integration, and version control is something a repository asks for rather than a product this build names. Admins can connect it on the Integrations page or keep the environment variables they already have, and repositories keep opening merge requests and reacting to comments and failed pipelines through the same webhook URL, with nothing to change at GitLab's end.
- A run that touches repositories on different providers now pins each provider separately, so disconnecting or reconfiguring one mid-run fails only the work that needed it, loudly and by name, instead of letting the rest of the run quietly pick up whatever is configured now.
- Importing a repository from a provider this build does not ship used to fail with a database error. It now says so in a sentence and names the providers you can import from.
- Disconnecting a provider now tells you which repositories it affects, not only which workflows and how many runs. A repository is what you are actually about to cut off.
- One setting goes away: `VCS_KIND` is no longer read. Which provider serves a repository comes from the repository record, and its credentials come from that provider's integration, so a deployment that still sets it can drop it. Leaving it set does nothing.
- A known limit, written down rather than discovered: one connection per integration means one GitLab host per deployment. Nothing in a repository's identity records which host it came from, so pointing an existing deployment at a second GitLab instance would silently retarget the repositories it already has.
